# Hardware-in-the-Loop Debugging

HIL is where AI assumptions break. The rule is simple: **read the device, don't
infer it.**

## Toolchain

- ST-Link + OpenOCD (`interface/stlink.cfg`, `target/stm32l4x.cfg` etc.).
- Build with `-g3` and keep the `.map`; static variable addresses come from it.
- A serial console or MQTT/can capture for end-to-end evidence.

## Basic recipes

```bash
# flash and run (mass-erase behavior depends on your Makefile)
openocd -f interface/stlink.cfg -f target/stm32l4x.cfg \
  -c "program build/firmware.elf verify reset exit"

# halt, inspect static state, resume
openocd -f interface/stlink.cfg -f target/stm32l4x.cfg \
  -c "init" -c "halt" \
  -c "mdw 0x20000b28 24" \
  -c "resume" -c "shutdown"

# read the map for symbol addresses
arm-none-eabi-nm -n build/firmware.elf | grep -E " s_state| s_count"
```

**Never leave the MCU halted.** A halted core stops feeding the watchdog only if
the debug freeze is configured; otherwise it resets, and the next probe finds a
booting device that looks "silent". End with `resume` or `reset run`.

## Evidence first

- Prove the state you think you are in: read counters, mode variables, backup
  registers (BKP), RTC alarm targets, GPIO config.
- Distinguish reset causes: capture `RCC->CSR` early in `main()` before HAL
  clears it; a standby wake may show no RCC reset flag at all.
- For "it is asleep / it rebooted / it is stuck" complaints, look for the
  discriminator: backup-register magic, reset-cause flags, boot counters.

## Timing measurement

- Instrument with a free-running tick counter and read the delta over SWD.
- Compare against the protocol timestamps and the PC clock.
- Measure the real link timeline: reset → first frame, command → ACK, standby →
  wake, group interval. Write the numbers down.
- Remember tool/transport overheads (server queues, modem reconnect) when
  attributing latency.

## Common traps

| Symptom | Likely root cause |
|---|---|
| Device "randomly" wakes every few seconds in Standby | IWDG not stopped in standby (option byte `FLASH_OPTR.IWDG_STDBY`) |
| Watchdog resets during debug | DBGMCU freeze bit not set / core halted too long |
| IWDG won't start | LSI not enabled first; PR/RLR only propagate after `KR = 0xCCCC` |
| WWDG unusable | PCLK1 too fast; the window is shorter than the loop |
| New firmware "didn't apply" | Flashed without erase, or config page kept — check both |
| Device ignores commands after reflashing | Stale broker/session state on the module; clean session and re-subscribe |
| 4G/MQTT data arrives coalesced or with a stray prefix | Modem packs serial bytes by idle time; separate channels with a gap > max pack time |
| First frame missing after reset | RS485 DE/RE tied together clips the first byte; recover or delay |
| Values drift over time | Clock source tolerance (LSI vs LSE); measure and compensate |

## Real-input rule

Synthetic events can pass where reality fails:

- A button bound to "press" may work when generated by automation and fail with
  a physical click (the OS cancels the action when the click completes). Test
  with real mouse/keyboard input when behavior depends on the OS/UI.
- A protocol parser may pass unit tests with clean input but fail on real
  captured bytes (whitespace bytes inside binary headers, prefix bytes,
  concatenated frames). Always replay captured traffic.

## HIL acceptance checklist

1. Repro captured before the fix (log/SWD/scope).
2. Fix verified with the same measurement.
3. Long-run check: at least one full cycle (boot → work → sleep → wake).
4. No regressions in adjacent features (frames continue, watchdog stays fed).
5. Device left in a sane state (factory or documented config, not mid-test).
6. Numbers recorded in the change log.
